# 整理设计：逐步实施方案

> 状态：规划稿（2026-09-25）。只分析与排期，不表示下述功能已实现，也不修改现有 Demo 的验收结论。原始需求以本目录七份主题文档为准；`docs/PROJECT_SPEC.md` 是既有四阶段 Demo 的基线，扩展功能须另立任务逐项验收。

本页是总览；具体到文件、接口、测试和状态流转的任务卡见[实施蓝图](../实施蓝图/README.md)。

## 一、现状与改动范围

当前可运行版本已有一名玩家、四只宠物敌人及 Boss、四把数据驱动武器、自动索敌与弹体、经验与三选一升级、五分钟对局和结算。当前暗色漫画素材已覆盖主要局内角色、场景及 UI。`GameSession` 直接启动一局；角色和武器由 `.tres` 定义；玩家持有运行时武器控制器与通用加成；`UpgradeSystem` 从固定池筛选并随机给出选项。现有系统没有开局菜单、角色/武器库选择、六格装备、防具、单件武器等级/互斥质变、金币存档或局外解锁。现有 `GameResult` 仅记录胜负、时间、等级、击杀数。

| 设计来源 | 已有可复用基础 | 主要新增或调整 |
| --- | --- | --- |
| [角色与敌人](角色与敌人/角色与敌人.md) | `CharacterDefinition`、通用玩家/敌人 Actor、波次导演 | 可选角色目录、角色被动与远程射手；新敌人/地图须先明确定位和波次。 |
| [系统规则](装备与战斗/系统规则.md) | `WeaponDefinition`、`WeaponController`、运行时修正 | 开局候选池、装备栏/获取约束、单件等级、互斥质变、联动条件。 |
| [武器方案](装备与战斗/武器方案.md) | 直线、回旋、环绕弹体及弹数/射程修正 | 弓、法杖、剑及其独立攻击形态；连发、范围伤害、持续效果、减速/冻结、近战扇形。 |
| [防具方案](装备与战斗/防具方案.md) | 生命组件、伤害事件、现有吸血 | 防御/闪避/免死结算、三类防具、科技套装及派生武器。 |

| [美术素材清单](美术素材清单.md) | 新画风已接入局内主流程 | 随功能分批补 C03～C08、D/E 类及菜单素材；现有飞叶刃/骨棒/铃铛逐帧动作等遗留单列。 |

## 二、先确定规则，再写实现

以下是设计稿尚未决定、会改变数据结构或玩家体验的事项。**建议值仅供讨论，未获确认前不得作为最终规则写死。**

| 决策 | 建议的首版约束 | 不确定时的处理 |
| --- | --- | --- |
| 十种候选武器 | 从已解锁武器中最多选十种；武器库不足十种时允许少选，不能为了满足数量制造空选项。 | 何时强制恰好十种、是否允许重复、起始武器是否占其中一格须确认。当前仅四把，不能直接强制十选。 |
| 六个装备位 | 建议武器和防具共用六格，已有装备升级不占新格；满格时不再出现获取选项。 | 武器/防具是否分栏、是否允许替换/丢弃、起始装备和套装占位须确认。 |
| 获取与质变 | 首版仍由升级三选一获取，不引入地面装备掉落；每件持有装备只选一个互斥质变，达到基础等级门槛后才出现。 | 具体等级上限、质变时机、分支专属升级上限、加权概率须先配置化定案。 |
| 属性与伤害 | 明确“索敌范围”和“弹体飞行距离”是两个参数；伤害先判免疫/闪避，再算防御，再扣血，再触发反伤/吸血/死亡。 | 防御公式、暴击、反伤触发条件、持续伤害是否吸血与免死冷却须写规则表及边界测试。 |
| 装备联动 | 附魔箭只在同时持有法杖且法杖已选质变时进入候选；科技三件套建议要求三件都进入科技分支。 | 法杖变更后的继承方式、套装效果失效/恢复、导弹和激光的获取方式须确认。 |
| 局外成长 | 永久数据与单局快照分离；存档版本化，缺失/损坏时安全回退，不写共享 `.tres`。 | 金币公式、永久属性上限/价格、成就触发和重置策略须定稿后再做商店。 |
| 新角色与敌人 | 先为射手确定一句话定位、被动公式和起始装备；新敌人先确定速度/生命/攻击与波次。 | 未定的额外角色、地图与装扮只保留规划位，不提前批量制图或编码。 |

每项决策落地时，先补一页具体数值与例子，再创建对应开发任务；不在代码中以隐藏常量代替产品规则。

## 三、建议的实施顺序

每行是一个里程碑；复杂里程碑须再拆成一次只做一个能力或一个分支的小任务，分别提交和测试。完成每个小任务后更新 `docs/TASKS.md` 与 `docs/CHANGELOG.md`，不要自动进入下一项。前一项验收未过时先修复再继续。

| 步骤 | 本轮只做什么 | 主要落点 | 完成与测试标准 |
| --- | --- | --- | --- |
| R0 规则冻结与回归基准 | 决定上表中影响首批功能的候选池、装备位、等级/质变、伤害顺序；记录现有四武器和结算行为。 | 新规则文档、针对现状的测试清单 | 规则无互相冲突；现有解析、启动、快速测试和一次人工完整五分钟游玩记录可复现。 |
| R1 开局配置骨架 | 增加主菜单的角色与候选武器选择，生成不可变的单局配置快照；`GameSession` 接收配置，保留当前直接启动入口供回归。暂不做存档/商店。 | `scenes/ui`、`scripts/ui`、`scripts/core`、角色/武器目录 | 选择不同配置能启动/重开，配置缺失安全回退；旧默认局仍可运行。 |
| R2 装备栏与候选过滤 | 增加单局装备清单/槽位计数，升级池按本局候选、持有状态、槽位过滤；UI 展示实际持有装备。暂不做防具和进化。 | 玩家运行时清单、`UpgradeSystem`、HUD | 满格不出现获取卡，未入候选池武器不出现；已有武器升级不误占槽；重开清零。 |
| R3 单件成长模型 | 把“装备基础等级—一次互斥质变—质变专属等级”表示为数据配置与单局运行时状态；先用一把已有武器验证筛选与效果。 | `data/weapons`/`data/upgrades`、玩家运行时状态、升级候选逻辑 | 同件不能选两条质变；前置、上限及不再出现的选项均有测试；共享 `.tres` 不变化。 |
| R4 通用属性与伤害基座 | 补齐防御、全武器射程等通用 Buff；给伤害结算建立可测试的防御/免疫/反伤扩展点，不先塞入具体防具。 | `HealthComponent`、`DamageEvent`、运行时属性/升级配置 | 数值叠加、上限、实际损血与吸血的顺序明确；原有伤害与暴击回归通过。 |
| R5 第一件防具 | 只加入基础盔甲及其“加防御、减移动速度、升级减轻惩罚”；验证防具与武器共槽规则。 | 防具定义/运行时组件、升级资源、UI 图标 | 穿戴/升级/满格/重开行为正确；速度和减伤不写入共享资源。 |
| R6 弓箭最小闭环 | 加入基础弓与箭、基础升级、开局候选/获取卡/装备栏；先复用现有直线弹体。 | 武器/弹体/升级 `.tres`、C03/D01 素材 | 自动攻击、射程、弹数/伤害、完整局与重开均正常；与旧武器同时持有可用。 |
| R7 弓箭质变切片 | 一轮只做一条：先多重射击，再万箭齐发；附魔箭等法杖效果和状态机制完成后再做。 | 发射调度、分支配置、升级筛选、C03/D02 | 每轮箭数与轮次数分开验证；穿透不误当“数量+1”；互斥分支与上限通过。 |
| R8 法杖与状态效果 | 先完成基础蓄力法球，再分轮做爆炸/火焰/威能/寒冰；需要时分别补 AoE、地面持续伤害、减速/冻结、分裂弹的通用能力。最后接附魔箭。 | `WeaponController`/弹体扩展、状态效果组件、C04/D02/E02/E03 | 每种效果的命中次数、持续时间、重复命中与目标死亡清理由专项测试覆盖；旧武器无回归。 |
| R9 防具分支与套装 | 盔甲分支逐条接入；再做头盔、手套基础和科技分支，最后三件套与发射器。 | 防具分支、被动计时、套装条件、派生攻击、C06～C08/E04/E05 | 反伤无递归死循环，失血/免死只触发约定次数，经验按秒正确，套装条件可进入/退出。 |
| R10 局外经济最小闭环 | 做场内金币、结算奖励只发一次、存档版本/读写与损坏回退；菜单显示余额。暂不做商店/成就。 | 掉落与结算、`user://` 存档、D03/F03 | 胜负及重开不会重复发奖；退出再进保留余额；损坏旧存档不使游戏无法启动。 |
| R11 解锁与永久成长 | 分别接入武器/角色解锁、共通属性购买与单局初始快照、Buff 刷新次数；再做射手角色。成就和装扮拆成后续独立任务。 | 档案数据、菜单、`CharacterDefinition`、Buff UI、B02/D04/D06 | 未解锁内容不可选；购买扣费及上限正确；永久加成只在开局复制，重开/读档一致。 |
| R12 内容与体验收尾 | 待剑/新敌人/地图规则补全后逐项做；补现有武器动作帧、头像、Boss 徽记与必要 UI；做完整五分钟、性能和数值回归。 | C02/C05、B07/B08/B10、F02/F05、波次/场景 | 新内容有独立规则和素材验收；密集敌人、升级、暂停、胜负、连续重开与跨平台启动均通过。 |

R7～R9 的分支数目多，必须再拆成单分支任务；不得把同一行的所有分支合并成一次大改。R12 中没有定稿的内容不作为前面里程碑的阻塞项。

## 四、实现边界与依赖

1. **数据与运行时分离**：角色、武器、装备、升级的静态定义仍用 Resource；单局配置、装备等级/分支、金币本局奖励与永久档案分别用运行时对象/存档表示。绝不修改共享 `.tres` 记录本局状态。
2. **组合根保持轻量**：`GameSession` 只组装依赖、转发信号和控制单局生命周期；装备过滤交给升级系统，伤害结算交给组件，档案读写交给独立服务。UI 不直接修改玩家内部字段。
3. **先做能力，再做实例**：多轮发射、AoE、持续伤害、状态效果、扇形近战、套装联动各自先做可测的通用接口，再由武器/防具数据引用；不为每把武器复制整套脚本。
4. **已有射程约束继续有效**：角色基础攻击范围与武器射程取较小值决定索敌；弹体能飞多远、火舌多长、近战斩击半径另有规则，不能共用一个含义不清的“范围”字段。
5. **事件只结算一次**：敌人死亡、经验/金币掉落、玩家死亡、结算奖励及重开均应有一次性防护；保存失败要显式提示且不能丢失仍在内存中的本局结果。
6. **美术按功能随批交付**：每个新角色/装备先定轮廓和名称，再做透明 PNG、所需动作帧、图标/特效，并在实际 1280×720 画面验收。保留旧资源和独立版本目录；不使用现成作品的人物、标志或专有造型。

推荐依赖链：`规则决定 → 开局配置 → 装备栏/候选过滤 → 单件成长 → 战斗基础能力 → 弓/法杖/防具分支 → 套装联动`；`结算事件 → 金币与存档 → 解锁/永久成长 → 更多角色`。美术与专项测试跟随相应功能并行准备，但只在该功能实现时接入。

## 五、每一步的统一验收

- 先为该步写数据/规则边界测试，再实现；覆盖前置条件、上限、重复选择、节点释放/重开和 Resource 隔离。
- 执行 Godot 4.7.1 编辑器解析、无头启动、该步专项测试及现有快速冒烟测试；新增场景或视觉效果还需在图形窗口人工检查。
- 涉及经济/存档时额外测试退出重进、旧版本/损坏存档、结算重复触发；涉及性能时沿用高密度敌人压力测试。
- 只有通过测试、记录命令与结果、更新任务及变更记录后，才把该步标成完成。当前尚未完成的五分钟人工游玩与长期平衡仍单独保留，不因这份规划而勾选。

## 六、暂不纳入首批实现

剑的完整分支、未定角色/敌人/地图、任务成就、装扮、商店复杂折扣与重置、更多联动，以及美术清单 G 类灵感包，都需要进一步设计。与微信小游戏迁移相关的引擎导出、性能/包体和平台能力是独立工程，不应混入本轮玩法扩展。若优先级变化，先调整本路线图和新任务，再动代码。
