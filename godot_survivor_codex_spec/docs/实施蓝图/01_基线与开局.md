# 01｜基线、开局配置和装备位

下列路径相对 Godot 项目根目录。新增脚本/场景名是建议；实施时先检查已有文件，不因计划名不同复制功能。每个 T 只修改本卡所需文件，并按[验证协议](验证协议.md)记录结果。

## T01 当前版本回归基准和规则定案

- 输入：`docs/TASKS.md` 的未完成项、`docs/PET_PLAYTEST.md`、现有四份 `data/weapons/*.tres`、`scenes/bootstrap/main.tscn`、`scripts/core/game_session.gd`、现有快速测试。
- 操作：列出现有武器 ID/攻击形态/起始与获取途径、升级池条目、胜负与重开状态；核查 `docs/整理设计/逐步实施方案.md` 中的“已有/缺失”是否仍准确。逐项处理[规则决策](规则决策.md) D01～D07 的首版约束，未定项保持“待确认”。
- 证据：Godot 版本、编辑器解析、主场景 300 帧启动、全部快速 smoke 的命令和退出码；GUI 实际五分钟游玩单独记录，没做不得勾选。保留原有 `docs/TASKS.md` 验收状态，不因计划修正而改写历史。
- 退出条件：有一份可重复的基准记录、规则没有互相矛盾、已知未验收项明确。此任务不新增玩法代码。

## T02 角色/武器目录与单局配置快照

- 输入：`CharacterDefinition`、`WeaponDefinition`、`player_default.tres`、四把现有武器、`GameSession.start_run()`。先确定 D01。
- 操作：建立只读角色/武器目录（Resource 数组即可，不引入插件），按 ID 去重并验证引用有效；暂把现有可玩内容视为默认可用，正式解锁筛选留给 T29。定义 `RunLoadout`/同等运行时数据，保存所选角色 ID、候选武器 ID、起始武器 ID。构造时复制数组，之后菜单改动不影响当前局。为旧直启入口生成等价默认配置。
- 接口建议：`validate(catalog) -> Array[String]` 返回错误；`GameSession` 可接收配置快照，若无配置沿用现有导出 `player_definition` 的行为。这里不修改 `CharacterDefinition.starting_weapons` 的共享资源。
- 测试：空/重复/未知 ID、起始武器不在候选池、库存少于十、配置对象被外部修改后的隔离；旧主场景直接启动、重开仍有武器。不要在只有四把武器时制造十个虚假条目。

## T03 主菜单选择与兼容启动

- 输入：T02 配置对象、`scenes/bootstrap/main.tscn`、`scenes/gameplay/game_session.tscn`、现有 HUD/结算面板。
- 操作：增加菜单场景，显示已解锁角色和武器；通过信号提交选中的 ID，统一入口校验并创建单局配置，随后进入 `GameSession`。返回菜单、开始游戏与重开要有清晰路由。保留一个可测试的默认直启入口，避免旧 smoke 因菜单阻断。
- 接口建议：菜单只发出 `start_requested(loadout)`；会话的启动配置在 `start_run()` 前注入，不让 UI 直接持有玩家节点。存档/商店不属于此任务。
- 测试：鼠标选择与按钮、空选择提示、同一按钮重复点击、返回再进入、默认直启、胜负后重开；GUI 核查 1280×720 中文、焦点与资源无缺失。

## T04 六格装备清单与升级获取过滤

- 输入：`PlayerActor.add_weapon()`、`has_weapon()`、`UpgradeSystem.can_offer()`、`LevelUpPanel`、HUD 武器栏；先确定 D02/D03。
- 操作：增加单局装备清单（ID、类别、槽位，先只接武器），所有新武器获取统一走一个 `try_acquire`/等效入口；起始武器也占格。升级池按 T02 候选池、已持有和空格过滤 `ACQUIRE_WEAPON`；已有武器专属升级照常可出。满格时从池中移除获取卡，不禁用所有升级。重开清单清空且重建。
- 接口建议：`can_acquire(definition) -> bool`、`get_equipped_count() -> int`、`equipment_changed` 信号；`UpgradeSystem` 读取清单/配置快照，不自己维护第二份装备数量。
- 测试：第六件可获得、第七件被拒；重复获取不占格；非候选武器不出现；满格后仍有通用选项；连续升级/重开不残留。当前只有四把武器，可在测试中构造临时定义验证第六/七件，不把测试资源加入玩家武器库。
