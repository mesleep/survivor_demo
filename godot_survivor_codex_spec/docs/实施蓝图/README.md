# 实施蓝图：文件驱动开发入口

> 规划文件，非完成声明。来源是 [`整理设计`](../整理设计/README.md) 的七份主题稿与[逐步实施方案](../整理设计/逐步实施方案.md)。原有四阶段 Demo 的 `PROJECT_SPEC.md` 和 `TASKS.md` 不因本蓝图自动改变。

## 文件如何驱动工作

1. 每次先读项目 `AGENTS.md`、`docs/PROJECT_SPEC.md`、`docs/TASKS.md`，再读本页、[规则决策](规则决策.md)、[任务索引](任务索引.md)和当前任务卡。检查 Git 状态与实际源码；任务卡的“建议接口”不是强制覆盖现有接口。
2. 从任务索引选择**一个**依赖已满足的原子任务；把其“输入、操作、测试、完成条件”当作本轮工作契约。实现中发现范围超出任务卡，先拆新卡或修订本卡，不顺手做下一项。
3. 先补专项测试，再做最小实现；完成后按[验证协议](验证协议.md)运行解析、启动、专项和回归。涉及画面、声音、手感的验收要在 GUI 中做，无法执行就标记未验收。
4. 把本次证据写进[执行记录](执行记录.md)，同时更新 `docs/TASKS.md` 与 `docs/CHANGELOG.md`。只在真实通过后改任务索引状态。失败则修复并重测；实质阻塞写明依赖和决策人。
5. 一项完成后再取下一项。若用户明确授权整条路线自动实施，可按顺序继续；否则遵守 `AGENTS.md` 的单任务停止规则。

文件是权威工作单：设计源稿描述意图，规则决策描述已选择的产品行为，任务卡描述当次可交付范围，执行记录保存证据。代码始终以实际仓库为准；发现文件与代码冲突，先更新文件并解释，不静默假设。

## 全局不变量

- Godot 4.7.1 / GDScript、原目录与中文开发文档；持续保持主场景可启动。
- `.tres` 是共享静态定义，局内等级/质变/属性与跨局档案各有独立状态，不能回写 `.tres`。
- 不靠复制整份角色、敌人或武器脚本实现新类型；组件、Resource、信号、初始化参数优先。
- 不删旧素材；新素材按 `docs/整理设计/美术素材清单.md` 的编号与透明图、帧、图标、实拍要求分批接入。
- 所有玩法数值（伤害、冷却、概率、上限、价格、经验曲线、生成/结算公式等）必须可配置，放在 `Resource` 或 `@export` 字段中，禁止写死在脚本里。
- 本蓝图没有授权推送远端、引入第三方插件或做微信小游戏迁移。
